Report for the Kentik API team

REST update ignores the documented asGroup / siteMarket body when the URL sets a nested field

Observed 2026-10-21 against the live V6 API on a lab account, with plain curl and grpcurl, and again with the Kentik community Python SDK. Schema checked: api-schema-public commit 9de9a68. Evidence scripts: reports/scripts/rest-body-merge/curl_repro.sh (live, no SDK), reports/scripts/rest-body-merge/live_probe.py (live, SDK), and reports/scripts/rest-body-merge/audit.py (offline).

Summary

Two REST update operations reject the request body that the published OpenAPI document describes: ASGroupService.UpdateASGroup and SiteService.UpdateSiteMarket. The body wraps the object in its camelCase JSON name (asGroup, siteMarket). The server reads the object only under its proto name (as_group, site_market), which is the name the URL template uses for the ID. The same request works over gRPC. A client that follows the OpenAPI document cannot update an AS group or a site market over REST.

The defect does not depend on the SDK. Plain curl requests give the same results as the SDK, and grpcurl with the same camelCase JSON succeeds over gRPC. The section Reproduce without the SDK lists every request and the real response.

OperationREST, body as documentedREST, proto-name body keygRPCClient
PUT /as_group/v202212/as_group/{asGroup.id} 400 request.as_group.name "received: undefined" 200, updatedOK, updatedcurl / grpcurl, and the SDK
PUT /site/v202509/site_markets/{siteMarket.id} 500 internal error (name:TypeError) 200, updatedOK, updatedcurl / grpcurl, and the SDK

What the contract says

The proto declares the rule with the proto field name in the path and body: "*":

// proto/kentik/as_group/v202212/as_group.proto, line 271
rpc UpdateASGroup(UpdateASGroupRequest) returns (UpdateASGroupResponse) {
  option (google.api.http) = {
    put: "/as_group/v202212/as_group/{as_group.id}"
    body: "*"
  };
}

The generated OpenAPI document (gen/openapiv2/kentik/as_group/v202212/as_group.swagger.json) publishes the path parameter as asGroup.id and the body as ASGroupServiceUpdateASGroupBody, whose only property is asGroup:

"parameters": [
  { "name": "asGroup.id", "in": "path", "required": true, "type": "string" },
  { "name": "body", "in": "body", "required": true,
    "schema": { "$ref": "#/definitions/ASGroupServiceUpdateASGroupBody" } }
]
"ASGroupServiceUpdateASGroupBody": {
  "type": "object",
  "properties": { "asGroup": { "type": "object", "properties": { "name": ..., "asn": ... } } }
}

The SDK sends exactly that body: {"asGroup": {"name": "...", "asn": ["..."]}}. UpdateSiteMarket has the same shape ({site_market.id}, body: "*", body property siteMarket).

Why we think the defect is in the API, not in the client

  1. The client sends the body that the published OpenAPI document defines, key for key.
  2. The proto3 JSON mapping requires every parser to accept both the lowerCamelCase JSON name and the proto field name (protobuf.dev, ProtoJSON format). asGroup and as_group are two spellings of one field, so a correct merge cannot lose either one.
  3. The 400 message names request.as_group.name. The server built request.as_group from the URL ({as_group.id}), and the body never reached that object.
  4. Test 4 sends both spellings. A correct parser treats them as one field. The server keeps the URL-side as_group object and drops asGroup without an error.
  5. The same service accepts camelCase on create (test 1), where the URL sets no field. The failure appears only when the URL sets a field inside the body object.
  6. The same update over gRPC succeeds with the same data, so the service logic behind the route works.
  7. Routes where the two names are the same (label, site) work, and the alerting route with the same shape works. So the cause is in how the as_group and site REST layers merge path and body, not in the shared gateway.

A likely cause: the REST layer turns {as_group.id} into {"as_group": {"id": "..."}}, merges that object with the JSON body as plain objects keyed by spelling, and then reads as_group. The fix is to normalize the body to one spelling (or to decode it with a ProtoJSON parser) before the path value is set.

Report for the Kentik API team. Observed on 2026-10-21 against the live V6 API on a lab account. We used plain curl and grpcurl, and then the Kentik community Python SDK. Schema: api-schema-public commit 9de9a68, which matches upstream HEAD 8ec5847 for these services.
