Report for the Kentik API / schema team

kptr and deviceconf declare public gRPC services with no HTTP bindings, so they have no REST surface at all

13 RPCs across two SERVICE_VISIBILITY_PUBLIC services are unreachable over REST because their google.api.http annotations are absent.

Filed byKentik Community Python SDK
Date2026-09-18
Repokentik/api-schema-public
Revision89684ba, 2026-09-24 (revalidated)
Affected RPCs13 (plus 3 excluded: 1 method-private, 2 likely intentional)
SeverityFunctional gap, not a defect

The ask

Add google.api.http bindings to the 13 RPCs listed below, or tell us they are deliberately gRPC-only.

Either answer is actionable. What is hard to work with today is the ambiguity: these services are annotated SERVICE_VISIBILITY_PUBLIC and ship definitions into the public schema repo, which reads as "this is public API", yet they produce zero REST paths, which reads as "this is not exposed". One of those two signals is wrong.

Summary

Every generated REST artifact in api-schema-public derives from google.api.http annotations on RPC definitions. Where the annotation is present, protoc-gen-openapiv2 emits a swagger path and the gRPC gateway exposes an HTTP route. Where it is absent, neither exists.

Auditing all 35 services that declare RPCs in the current schema shows the convention is close to universal:

GroupServicesRPCsAnnotation coverage
Fully annotated32192 100% every RPC carries a binding
No annotations at all316 0% no swagger paths, no gateway routes
Partially annotated00 No service mixes the two, which is why the three outliers look like an oversight

There is no middle ground anywhere in the schema. A service either annotates every RPC or none of them. That pattern is what makes us think these three were missed rather than excluded on purpose.

Why kptr matters to SDK consumers

kptr is the reverse-DNS (PTR) enrichment service. Its four RPCs split into two planes, and the split is what makes the missing bindings consequential:

RPCPlaneRequired metadataPurpose
GetNetworkRangeAssignmentsAgent x-kt-agentid, x-kt-sid Agent asks which IP prefixes it must resolve
UpdateAddressNamesAgent x-kt-agentid, x-kt-sid Agent submits resolved IP-to-hostname mappings
ResolveAddressesCustomer Email plus API token only Resolve a list of IP addresses to hostnames
ListResolvedAddressesCustomer Email plus API token only Pull the company's entire resolved-address table for local caching, instead of synchronous per-flow lookups

The bottom two require nothing beyond a standard API key, per the service's own comments. "Give me hostnames for these IPs" and "give me the whole PTR table" are ordinary customer-facing capabilities, and today there is no way to invoke either over REST.

The audit script counts annotations per RPC block rather than per file, so an RPC using additional_bindings is counted once.

Suggested fix

For each affected RPC, add the binding the rest of the schema already uses. For the two customer-plane kptr RPCs, something along these lines would be enough for the gateway and every downstream generator to pick them up:

 rpc ResolveAddresses(ResolveAddressesRequest) returns (ResolveAddressesResponse) {
   option (kentik.core.v202303.method_scope) = "kptr:read";
+  option (google.api.http) = {
+    post: "/kptr/v202602/addresses/resolve"
+    body: "*"
+  };
 }

 rpc ListResolvedAddresses(ListResolvedAddressesRequest) returns (ListResolvedAddressesResponse) {
   option (kentik.core.v202303.method_scope) = "kptr:read";
+  option (google.api.http) = {
+    get: "/kptr/v202602/addresses"
+  };
 }

Path shapes are yours to choose. We have no requirement beyond the bindings existing. If the agent-plane RPCs should stay gRPC-only because they depend on x-kt-agentid and x-kt-sid metadata, annotating only the two customer-plane RPCs would resolve the practical problem.

Questions for the API team

  1. Are kptr and deviceconf intended to be reachable over REST? If yes, the bindings are simply missing. If no, we will document them as gRPC-only.
  2. If they are deliberately gRPC-only, should SERVICE_VISIBILITY_PUBLIC still apply? Today that annotation is the only public signal, and it currently points the opposite way from the absent bindings.
  3. Is there a convention we should follow for distinguishing agent-plane RPCs (those requiring x-kt-agentid and x-kt-sid) from customer-plane RPCs? A machine-readable marker would let SDK generators omit agent-plane operations automatically.
