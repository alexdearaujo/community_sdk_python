Pre-PR audit of the V6 SDK branch

This report lists the defects that an audit found on branch FA-2-Update-the-python-SDK-from-V5-to-V6 at commit 6e76b43, on 2026-10-10. Nine parallel audits covered the hand-written runtime, the gRPC bridge, the generator, the generated code, the tests, packaging, CI, the release tooling, and the docs. The main session reproduced the most severe findings a second time.

The audit made no call to the real Kentik API. It ran no e2e test (an end-to-end test against the real API) and did not read .env. It changed no tracked file and pushed nothing. The reproduction scripts are in evidence/. Some of them expect the scratch layout that they ran in, so read them as records, not as ready tests.

Summary

The baseline is green:

  • uv run poe test gave 2948 passed, 145 skipped, and 468 e2e deselected.
  • Ruff lint, Ruff format, ty, uv run poe check-specs, and the Sphinx -W build passed.
  • A fresh regeneration at api-schema-public 9de9a68 is byte-identical to the committed tree. That commit is the upstream HEAD on 2026-10-10.
  • The regeneration gives the same bytes across hash seeds, working directories, and a fresh Python 3.12 toolchain.

The green suite hides real defects. The mocked tests build their sample responses from the generated models, so they cannot see a model that disagrees with the schema. The REST e2e layer never reaches Kentik, and both e2e layers pass on any SDK error. Two model bugs and a lost gRPC service passed all 2948 tests. The diagram shows the gap in each gate.

Blockers

B1. A new enum value from the server breaks the whole call

Where: the 97 generated (str, Enum) classes, and httpx.jinja2:33, which builds the response model with no guard.

The generated enums reject any value that they do not list. When Kentik adds a value, every installed SDK version fails on each response that contains it. The error is a pydantic.ValidationError. It is not a KentikError, but error_handling.md:48 says that except KentikError catches everything.

This happens in practice. Upstream commit 8eb47aa (2026-08-18) added LANDING_TYPE_AI_ADVISOR. One user with that landing page makes client.user.list_users() fail for the whole account. 99 of 234 operations return a model that reaches one of 79 enums. The gRPC audit found that 96 of the 228 gRPC-covered operations fail on both transports.

Evidence: Reproduced. A mocked list_users response with an unknown defaultLandingPageType raised a ValidationError of type enum.

Fix in: a template. Override the enum template of the generator and add a _missing_ hook that returns a pseudo-member for unknown names and numbers. The generated-code audit tested this approach with pydantic. Also wrap a response parse failure in a KentikError subclass that keeps the raw body and rate_limit.

B2. Alert.acknowledgement has the wrong type

Where: generate_sdk.py:193-197, in clean_schema_names.

The alert swagger defines an object AlertAcknowledgement (state, ackedByUser, autoAckId, ackedAt) and an enum v202505AlertAcknowledgement. When the generator strips the version prefix, the enum overwrites the object with no warning. Alert.py:42 then types the field as the enum.

Any alert that carries an acknowledgement makes alert_list, alert_get, ack, and un_ack raise ValidationError, on REST and on gRPC. For ack, the server performs the action and then the SDK raises, which invites a retry. This is the only such collision in the 89 swagger files.

Evidence: Reproduced by four audits. The main session read both schemas in alert.swagger.json.

Fix in: the generator. When the short name already exists, keep the prefix or fail the run. Add the same guard for model files that two swagger files write. 43 model names repeat across files today, and all of them are identical.

B3. ExternalContext requires both members of a oneof

Where: ExternalContext.py:17-19. Upstream alert.proto:484-498 marks servicenow and jira_cloud as REQUIRED. Both sit inside oneof context, a proto group where at most one field is set.

Any alert linked to an external ticket fails with jiraCloud Field required. set_external_context cannot work. The model needs both members, and the server rejects a body with both.

Evidence: Reproduced on both transports. This is the only oneof with more than one REQUIRED member.

Fix in: the generator, and upstream. Drop oneof members from required, with the oneof index from the compiled descriptors. Report the annotation upstream.

B4. gRPC lost MitigationsService to a file-name collision

Where: generate_sdk.py:496-497 copies every compiled proto into one flat pb/ directory by file name.

alerting/public/v202505/mitigation.proto declares MitigationsService with 6 RPCs. alerting/types/v202506/mitigation.proto compiles to the same file name and overwrites it. The generator prints no warning. These 6 methods raise NotImplementedError on gRPC:

  • mitigations_list, mitigations_create, and mitigations_get
  • act
  • available_actions and available_actions_for_mitigation

The docs blame upstream. rest-vs-grpc.md:129, CHANGELOG.md:95, and the alerting service page say that no proto declares the service. test_wrapper_generation.py:258 asserts the bug as the expected result.

Evidence: Reproduced. The committed mitigation_pb2.py names the types/v202506 source, and no alerting pb file contains MitigationsService.

Fix in: the generator. Keep the proto package tree under pb/. Fail on a duplicate file name. Relink imports by package, not by file stem. The fix gives gRPC 234 of 234 operations. Then correct the test, the docs, and the CHANGELOG.

B5. A malformed credential leaks the API token into the error text

Where: rest_runtime.py:91-94 copies the httpx error text into TransportError.

A token from a password manager CLI often ends in a newline. The HTTP library rejects the header, and the message becomes ListUsers transport failed: Illegal header value b'<token>\n'. The full token then reaches logs, CI output, and error trackers. An email with a trailing space leaks the same way. A non-ASCII value raises a bare UnicodeEncodeError.

Evidence: Reproduced against a local socket.

Fix in: the runtime. Strip the email and token once, in KentikAPI and APIConfig. Reject control and non-ASCII characters with a ConfigurationError that names the field, never the value. Do not copy httpx.LocalProtocolError text into an exception.

B6. A gRPC call after close() crashes the interpreter

Where: grpc_client.py:98-99 closes the channel. The deadline interceptor at grpc_client.py:40-53 still calls into it.

A wrapper call after close(), or a call that races shutdown, kills the process with a segmentation fault (exit 139). There is no traceback and nothing to catch. The root bug is in grpcio 1.84.0, but only the SDK can stop it. REST raises ConfigurationError in the same case.

Evidence: Reproduced 3 of 3 times, with a localhost target. Another call path raises the builtin ValueError instead.

Fix in: the runtime. Keep a closed flag on GrpcTransport. Make the interceptor raise ConfigurationError before it calls the channel.

B7. gRPC ignores the credentials and host of an override

Where: grpc_runtime.py:125-136 takes only grpc_deadline from api_config_override. The channel binds the credentials and target at grpc_client.py:83-91.

A script that serves several accounts passes an override with tenant B credentials to a tenant A client. REST acts as tenant B. gRPC acts as tenant A, for writes too. An override with no credentials raises on REST but runs on gRPC. The CHANGELOG mentions the limit. The quickstart says that an override carries its own credentials, with no gRPC exception.

Evidence: Reproduced with an in-process gRPC server, which saw the tenant A credentials.

Fix in: the runtime. When the override credentials, base_path, or verify differ from the transport values, raise ConfigurationError. As an alternative, build the auth metadata per call in the interceptor.

B8. httpx 1.0 will break import kentik_api

Where: pyproject.toml:30 declares httpx>=0.28.1 with no upper bound. api_config.py:9 imports the private httpx._utils.

httpx 1.0.dev4 to 1.0.dev6 are on PyPI, and they have no httpx._utils. When 1.0 final ships, every fresh install resolves to it. The import then fails with ModuleNotFoundError.

Evidence: Reproduced in a throwaway venv with httpx==1.0.dev6.

Fix in: packaging and the runtime. Cap httpx<1 now. Replace the private import with urllib.request.getproxies() and proxy_bypass. The surface alert treats a changed requirement as breaking, so add a CHANGELOG line.

B9. gRPC responses over 4 MiB fail and look like a quota error

Where: grpc_client.py:88-91 passes no channel options, so grpcio keeps its 4 MiB receive limit. Version 1.0.7 set 40 MB. grpc_runtime.py:28 maps RESOURCE_EXHAUSTED to 429.

A large account calls list_devices(), and the response exceeds 4 MiB. REST returns the data. gRPC raises HTTPException(429) with a rate_limit that is not exhausted. The rate-limiting guide tells callers to back off on 429, so the retries fail forever.

Evidence: Reproduced with a local server that returns 5 MB. Real Kentik responses over 4 MiB are likely, but nobody measured one.

Fix in: the runtime. Set grpc.max_receive_message_length on the channel, and expose channel options. Classify the client-side size error apart from quota. Add the change to migrating-from-1x.md.

B10. Enum members in a path or query go out as ClassName.MEMBER

Where: rest_runtime.py:33 formats path values with format(). Query values at rest_runtime.py:77-79 reach httpx unchanged, and httpx calls str().

client.device.list_devices(view=DeviceView.DEVICE_VIEW_FULL) sends view=DeviceView.DEVICE_VIEW_FULL. A policy_get call with PolicyType.POLICY_TYPE_AGENT builds /v202505/policies/PolicyType.POLICY_TYPE_AGENT/1. The parameters are typed str, and the generated enums subclass str, so type checkers accept the call. gRPC sends the correct value. At least 12 parameters across 9 operations take enum values.

Evidence: Reproduced on Python 3.12 and 3.14.

Fix in: the runtime. Unwrap Enum to .value in path_segment and in query cleaning, list items included.

B11. Public names are not stable, and 2.0.0 will freeze them

Three naming rules make user code break on a routine schema update:

  1. wrapper_generation.py:312-325 gives a bare method name to the module that sorts first. Today client.alerting.list, get, create, delete, and replace act on auto-ack rules, and the alert list is alert_list. A new upstream module that sorts earlier points these five methods at other endpoints. A regeneration experiment showed this, and the surface record reported no breaking change.
  2. 12 method names carry a service prefix from upstream operationIds, joined with __, for example route_service__announce. They are in kagent (8), ktbgp (3), and nms (1).
  3. 50 model class names keep a version string, for example labelv202210Label, devicev202504beta2Label, and typesv202506PaginationConfig. A version bump renames them. README.md:13 says that the pipeline removes these prefixes.

Evidence: Reproduced.

Fix in: the generator, before the first 2.0.0 release. Prefix every operation name that is not unique in its service. Strip service prefixes from operationIds. Strip version tokens in all positions, and fail on a resulting collision. Record each client.<service>.<method> in api_surface.json.

B12. The per-operation error class is never raised

Where: error_package.py:266 makes each leaf class, for example ListDevicesUnexpectedError, a subclass of the service error. The operation class from error_package.py:276 is not its parent.

except ListDevicesError: catches nothing. REST raises ListDevicesUnexpectedError, and gRPC raises the base HTTPException. The error guide documents the gRPC difference. CLAUDE.md says that both transports raise the same type.

Evidence: Reproduced with a mocked 404.

Fix in: the generator and the runtime. Make each leaf class a subclass of its operation class. Pass the operation error class to call_grpc, so that gRPC raises the same type.

B13. The e2e layer proves nothing

Four defects stack up:

  1. The REST e2e never reaches Kentik. tests/_discovery.py:199-206 gives api_config_override a sample APIConfig for https://api.example.com. test_endpoints_e2e.py:61 fills every parameter. All 100 REST calls go to that host and raise TransportError.
  2. The pass rule accepts any KentikError, in test_endpoints_e2e.py:65-77 and test_endpoints_e2e_grpc.py:63-81. A revoked token or a network outage stays green. No test asserts the response type.
  3. Without credentials, the fixtures error instead of skipping. conftest.py:23 and conftest.py:40 catch ValueError, but KentikAPI raises ConfigurationError.
  4. Any -m expression replaces the default marker filter at pyproject.toml:92. The command pytest tests/ -m "not slow" collects all 468 live tests, which use the credentials in .env. The live tests issue only GET calls.

Evidence: Reproduced with mocked replays of the e2e calls and with --collect-only.

Fix in: the tests.

  1. Pass no override in e2e.
  2. Accept only HTTPException, plus NotImplementedError for a listed unrouted operation.
  3. Assert the return type.
  4. Get real IDs with a list call before each get call.
  5. Catch ConfigurationError in the fixtures.
  6. Gate the live layer behind an explicit flag in tests/e2e/conftest.py, and add --strict-markers.

Generation pipeline

These defects decide whether a schema sync stays cheap.

P1. protoc failures do not fail generation

Where: generate_sdk.py:504-515 and generate_sdk.py:346-347 only print a protoc error.

In a scratch copy, one syntax error in vault.proto gave exit 0 and "Generation Complete". The vault and credential services lost all their pb files, and their wrappers became REST-only. The surface record reported no change, and check-changelog passed. B4 passed every gate the same way.

Fix in: the generator. Exit non-zero on any protoc failure. Record the gRPC route of each operation in api_surface.json, and treat a lost route as breaking.

P2. The generator toolchain is not pinned

Where: generate_sdk.py:52-66 runs uvx openapi-python-generator with no version. The tool is not in pyproject.toml or uv.lock.

CI resolves the newest generator on every run, but the fixups match the exact output of version 2.1.2. A new generator release can fail the determinism job on unrelated PRs, and a local run cannot reproduce that failure. Also, a run from outside the project directory resolves grpcio-tools fresh through uv run --with grpcio-tools, and grpcio-tools 1.85.0rc1 shipped on 2026-10-09.

Fix in: the generator. Add openapi-python-generator==2.1.2 to the dev group and call it with uv run. Drop --with grpcio-tools. Pass --project to every inner uv call. Add a pin test.

P3. CI follows a moving schema, and nothing syncs the repo

Where: the generated-output-matches-schema-head job at tests.yml:101-132.

The job regenerates from upstream HEAD on every PR and fails on any difference. Upstream changed generator inputs 17 times in the last 90 days, so every open PR and main turn red until someone regenerates. No file records the schema commit, so nobody can rebuild an old tree without the commit messages. There is no scheduled sync job, and there is no Dependabot or Renovate configuration. The actions use old major versions without SHA pins.

Fix in: CI.

  1. Commit the schema commit hash, for example in api_surface.json.
  2. Make the PR job regenerate at that pinned commit.
  3. Add a scheduled job that moves the pin to upstream HEAD, regenerates, and opens a PR with the surface alert.
  4. Add dependabot.yml for github-actions and uv.
  5. Pin the actions by SHA.

P4. Generation is not atomic

Where: generate_sdk.py:376-393 wipes gen/ before most of the work. The parity check runs later, at generate_sdk.py:528.

If upstream renames its files so that no file matches, the pre-wipe test passes on an empty list. The run wipes gen/ and then fails. client_mixin.py still imports the deleted wrappers, so import kentik_api fails until a git checkout. Any abort after the wipe has the same result.

Fix in: the generator. Before the wipe, compare the schema directories with the selected services, and require at least one file. Build into a staging directory and swap it in only on success.

P5. Version selection compares strings

Where: parity.py:54.

v202504beta2 wins over GA v202504, beta9 wins over beta10, and v20260515beta1 wins over v202605. No current service triggers this.

Fix in: the generator. Compare a parsed tuple of date, stage rank, and stage number. Fail on a version name that does not parse.

P6. The surface record and the changelog gate miss breaking changes

Where: api_surface.py:133-152 and release_notes.py.

  • The record keeps only the operation id, the status, and the required parameter names. It does not keep wrapper names, optional parameters, types, return models, or error classes. A removed view parameter, a retyped parameter, or a list that calls another endpoint all pass.
  • release_notes.py:82 accepts any substring. "Service removed: client.nms" passed, because the word nms is in the Added section.
  • An unresolvable --since ref exits 0, at release_notes.py:127-135. For this PR, the merge base has no api_surface.json, so the CI changelog job tests nothing.
  • A version bump reports every operation as removed, because the key is the literal path.
  • The default baseline is the newest tag by date, not an ancestor tag, at release_notes.py:47-68. A hotfix after a newer minor release, or a final release after an rc, compares against the wrong tag.
  • The dependency diff calls any spec change a raised floor. It ignores python-dotenv, googleapis-common-protos, and requires-python.

Fix in: the release tooling.

  1. Record each wrapper method with its path, parameters, types, return type, error class, and gRPC route.
  2. Require an exact token from each breaking change, in lines that the PR added.
  3. Fail on a ref that does not resolve.
  4. Use ancestor tags, sorted by version.
  5. Parse requirements with packaging.

P7. The generator writes into the schema checkout

Where: generate_sdk.py:248-254 writes tmp*.json next to each swagger file.

A read-only checkout fails, and a killed run leaves files behind. No swagger file has an external $ref, so the location has no purpose.

Fix in: the generator. Use a TemporaryDirectory.

What works

  • Regeneration is deterministic, and it matches upstream HEAD byte for byte.
  • All 234 swagger operations line up with 234 REST functions and 234 wrapper methods. The query, path, body, and status declarations match.
  • gRPC response parity holds for all 228 routed operations. Request round trips match for 227.
  • The wheel installs and imports all 1316 modules on Python 3.12, 3.13, and 3.14. The lowest allowed dependency set passes the smoke, runtime, and generated suites.
  • The protobuf and grpcio floors match the generated code.
  • path_segment encodes reserved characters and refuses dot segments. The client does not follow redirects, so auth headers cannot reach another host.
  • Proxies, NO_PROXY, .env parsing, and with_timeout connection sharing work as documented.
  • The suite has no order dependence and no hidden network use.

Post-merge automation setup (ledger entry P3a)

After the V6 branch merges into main, complete these steps:

  1. Turn on Settings > Actions > General > Allow GitHub Actions to create and approve pull requests. The weekly schema-sync job fails without it.
  2. Run schema-sync once by hand from the Actions tab. Confirm that it ends with "already matches schema HEAD" or opens a pull request.
  3. Expect Dependabot pull requests for the action SHA pins and uv.lock.
  4. Close and reopen each schema-sync pull request to start its CI. The steps are in "Automated update pull requests" in the generation guide.
