The ask

Tell us what SERVICE_VISIBILITY_PRIVATE is meant to mean, and whether these services should be reachable from a community SDK.

We are not asserting a security vulnerability. These endpoints enforce their own authentication and authorization, and we have not tested whether an ordinary customer token is accepted by them. What we are flagging is that the only machine-readable visibility signal in the schema is currently being ignored by every downstream generator, including ours, and we would rather honor it than guess.

Summary

The schema annotates service visibility with option (kentik.core.v202303.visibility). Across the current schema there are 67 such service annotations, and five of them are non-public. Four of those five belong to three services, and every one of those services also carries google.api.http bindings, so protoc-gen-openapiv2 publishes REST paths for them into gen/openapiv2/ in the public repo. The fifth, diagnostic (SERVICE_VISIBILITY_PUBLIC_KENTIK), has no HTTP bindings and publishes no paths.

Because the visibility annotation is a custom option that lives only in the proto layer, it does not survive into the generated swagger. Downstream generators consume swagger, so the signal is lost entirely. The Kentik Community Python SDK generates its client surface from those swagger files and therefore mounts all three services without ever seeing the annotation.

The inverse case is also true, and it is what led us here

kptr is annotated SERVICE_VISIBILITY_PUBLIC and has no REST surface, because its RPCs lack HTTP bindings. So the SDK currently ships the exact opposite of what the annotations describe: it exposes three services marked non-public, and omits one marked public. That inversion is covered in a companion report, "kptr and deviceconf declare public gRPC services with no HTTP bindings".

Worth a second look independently: ktbgp's paths are /routes/announce, /routes/list, and /routes/withdraw. They carry no service prefix and no version segment, unlike every other service in the schema. If these are ever meant to be public, the path shape looks unintentional.

3. The SDK generates callable methods for all of them

These are real methods on the public client object, generated automatically and shipped:

client.ktbgp.route_announce()
client.ktbgp.route_list()
client.ktbgp.route_withdraw()

# vault, SERVICE_VISIBILITY_PRIVATE
client.vault.list_secret()
client.vault.get_secret()

# kagent CapabilityAdminService, SERVICE_VISIBILITY_PRIVATE
client.kagent.list_capabilities()
client.kagent.create_capability()
client.kagent.get_capability()
client.kagent.delete_capability()
client.kagent.update_capability()

# kagent CapabilityReleaseService, SERVICE_VISIBILITY_PROTECTED
client.kagent.get_capability_release()
client.kagent.get_capability_latest_releases()
client.kagent.get_capability_supported_distros()

The one we would most like a direct answer on

client.vault.get_secret() and client.vault.list_secret() are secret retrieval operations, on a service the schema marks PRIVATE, published as unauthenticated-looking GET routes in a public schema repo, and generated into a community SDK. Whatever the server-side authorization actually does, this combination is worth a deliberate confirmation rather than an assumption.

4. Visibility distribution across the whole schema

$ grep -rhoE 'visibility\) = [A-Z_]+' proto/ | sort | uniq -c | sort -rn

  62 visibility) = SERVICE_VISIBILITY_PUBLIC
   3 visibility) = SERVICE_VISIBILITY_PRIVATE
   1 visibility) = SERVICE_VISIBILITY_PUBLIC_KENTIK
   1 visibility) = SERVICE_VISIBILITY_PROTECTED
   1 visibility) = METHOD_VISIBILITY_PRIVATE

Four distinct non-public values are in use and we have no documentation for any of them. PUBLIC_KENTIK (on diagnostic) and PROTECTED (on CapabilityReleaseService) are particularly opaque. There is also a single METHOD_VISIBILITY_PRIVATE, on deviceconf's ExecuteCommand RPC, which shows that per-method granularity exists and that a per-service rule would miss it.

  kagent.CapabilityReleaseService: SERVICE_VISIBILITY_PROTECTED   (REST paths published: 17)
  ktbgp.RouteService: SERVICE_VISIBILITY_PRIVATE                  (REST paths published: 3)
  vault.VaultService: SERVICE_VISIBILITY_PRIVATE                  (REST paths published: 2)

The path counts for kagent are per service directory, not per proto service. The per-service breakdown in section 2 above is the precise one.

Why this is hard to resolve on our side

The SDK is generated end to end from the swagger files. It never reads the protos. Three options exist and all of them need your input:

OptionWhat it needs from the schemaTrade-off
Propagate visibility into swagger Emit the annotation as a vendor extension, for example x-kentik-visibility, on each operation or tag Preferred. Self-maintaining, works for every downstream generator, and supports per-method granularity
Stop publishing private services to the public repo Exclude non-public services from gen/openapiv2/ and gen/openapiv3/ Cleanest boundary, but may break internal consumers that rely on the published artifacts
SDK-side deny-list Nothing Last resort. Hand-maintained, silently goes stale as the schema evolves, and duplicates a fact the schema already knows

Questions for the API team

  1. What do SERVICE_VISIBILITY_PRIVATE, PROTECTED, and PUBLIC_KENTIK each mean? Is any of them intended to mean "do not expose in a customer-facing SDK"?
  2. Should ktbgp, vault, and the two kagent capability services be reachable by customers holding an ordinary API token?
  3. If not, can the visibility annotation be propagated into the generated swagger as a vendor extension so downstream generators can honor it without a hand-maintained list?
  4. Should services marked non-public be published to gen/openapiv2/ and gen/openapiv3/ in the public repo at all?
  5. Is ktbgp's unversioned, unprefixed path shape (/routes/announce) intentional?

If the answer to question 2 is "no", removing these from the SDK is a breaking change to its public surface, so we would want to coordinate timing and a deprecation note.
